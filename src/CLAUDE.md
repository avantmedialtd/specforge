# Frontend

**The same bundle runs in two hosts.** `src/api.ts` gates on `isTauri()`: `invokeLogged` dispatches to Tauri's `invoke` in the desktop app and to `webInvoke` (`POST /api/invoke`) when served by `specforge-web`. So **adding a command touches four places**, not one:

1. `src/api.ts` — the wrapper
2. `crates/specforge/src/commands.rs` — the `#[tauri::command]` handler
3. `crates/specforge/src/lib.rs` — the `tauri::generate_handler![…]` list
4. `crates/specforge-web/src/dispatch.rs` — a match arm in the `/api/invoke` table

Miss step 4 and the command works in `bun tauri dev` and fails at runtime in the browser with `unknown command: X`. Neither `tsc` nor `cargo` catches it, and the served web UI is the preferred path for visual verification — so this is the failure you are most likely to hit.

Five commands break that rule on purpose. `open_pull_request`, `open_pull_request_window`, `open_pull_request_link`, `set_pull_request_window_size` and `open_image_window` have **no** `dispatch.rs` arm, so the web transport has no operation that opens a URL or a window on the serving host (`web-ui`: *Link Handling in the Browser Skin*). In the browser skin, a pull-request row or chip links to its SpecForge `/pr/...` address, the pull-request view's provider control and content links are opener-isolated `target="_blank"` links, and a new window, a zoom window included, is a `window.open` tab. `dispatch::tests` pins each command as unknown there. Don't "fix" the missing arms.

Events split the same way: `listenLogged` uses Tauri `listen` in the desktop app and an `EventSource` against `/api/events` in the browser (served by `crates/specforge-web/src/sse.rs`). A new event name needs the SSE side too. Names and payload shapes are owned by `crates/openspec-app/src/events.rs`; `src/types.ts` re-declares the same string literals by hand. The pull-request panels brought three: `bitbucket-pull-requests-updated` and `github-pull-requests-updated` (`CacheEvent`s, payload-less — re-read with `get_bitbucket_pull_requests` / `get_github_pull_requests`; the provider-less `pull-requests-updated` and `get_my_pull_requests` are retired and must not come back), and `pull-request-panel-moved` (a direct emit from `set_bitbucket_panel_position` and `set_github_panel_position` on both transports, carrying `{ provider, position }` — a listener re-seats only the named provider's panel). The Commit history switch brought one more: `commit-history-enabled-changed`, a direct emit from `set_commit_history_enabled` on both transports carrying the new boolean — never a cache event. The pull-request viewer brought two **service notices**:
- `review-progress-changed`, carrying the reference;
- `pull-request-provider-changed`, carrying `{ provider, enabled }`.

`AppService` raises them on its own broadcast (`subscribe_notices`). `spawn_notice_forwarder` carries them to every desktop window, and the SSE stream's notice arm carries them to every tab, so a mark or a toggle made anywhere reaches every view of one service. They are never a cache event and never a direct emit.

**The pull-request view.**
- **Address and opening.** A `pullRequest` address (`/pr/<github|bitbucket>/<owner>/<repo>/<number>`) names a pull request by reference, never by URL. `resolvePullRequestAddress` (`src/routing/resolve.ts`) resolves it against both snapshots and both enabled flags. It opens like a document: a click shows it in the center pane, and the new-window gesture or the pop-out control opens the pull-request window.
- **The window.** A detached kind of its own, with the query flag `?pullRequest=1&at=<address>` and the label `pull-request-<hash>`. Its capability, `crates/specforge/capabilities/pull-request.json`, grants listen, unlisten and close only. It is the only window whose `head` carries a content-security policy (`src/windowKind.ts`).
- **Commands.** Six shared commands: `get_pull_request_detail(reference, manual, cachedOnly)`, `get_pull_request_file`, `get_pull_request_file_image`, `get_review_progress`, `set_file_viewed` and `set_hunk_viewed`. `get_pull_request_file_image` answers a `PullRequestImageOutcome` (`images`, `changed` or `failed`, whose reasons add `redirected`), read only when the reader activates "Show image". An image file links to its diff on the host when it is an LFS pointer, its read failed as `redirected` or `unavailable`, or a version is refused or undrawable (`imageReadLinksToHost`, plus `DiffView`'s `onImageUndrawable`). The hunk states in `get_review_progress` are positional, so the view applies them only to the detail whose `headCommit`/`baseCommit` they name (`hunkStates`). The three desktop-only ones are above. `get_pull_request_file` answers a `PullRequestFileOutcome`: the file, `changed` (only this makes the view read the pull request again) or `failed` with a reason the view words (`fileFailureText`). A file GitHub sent without its patch arrives withheld, and its first load is a file read from GitHub; a file still too large links to its diff on the host (`hostFileLink`, anchored by `src/sha256.ts`).
- **Untrusted content.** Pull-request text renders only through `MarkdownView`'s pull-request mode (`src/pullRequestMarkdown.tsx`): no raw HTML, comments dropped, mermaid shown as its source, no remote images, no ids taken from the content, and desktop links only through `openPullRequestLink`.
- **Decisions.** The view's decisions live in `src/pullRequestView.ts`, tested there: the read triggers (never a timer), the thread split, and the wording.

**One diff renderer.** `src/components/DiffView.tsx` is the only component that draws a diff. Every host (commit detail and the pull-request view) passes it the model (`DiffFile[]`, mirrored in `src/types.ts` from `openspec-core`'s `diff.rs`), the names of its two sides, a loader for withheld files, and at most two per-file slots: `renderFileHeaderExtra` inside the sticky header and `renderFilePreamble` above the first hunk. Per hunk, `hunkSlots` adds a heading extra in the heading row's gutter, an end row, and the hunks the host folds; a fold the reader shows is view state, dropped when the host stops folding that hunk. A `ref` (`DiffViewHandle.collapse`) lets a host collapse a section once, which the header toggle reverses. Folds, shows and collapses keep one row in place (`recordPlace`/`anchorAt`/`restoreAnchor`), recorded during the render that changes them, while the page still shows the old folds. A host never gets a second renderer or a column of its own. A host may also pass `readImage` with `imageReads`. An image file (`isImageFile`: one of eight extensions, and binary, hunk-less or an LFS pointer's diff) then shows its two versions in place of its state row. Commit detail reads `"nearView"`: one `IntersectionObserver` rooted at the scroll port, with a one-viewport margin, feeds `NearViewQueue`, two reads at once. The pull-request view reads `"onRequest"` behind "Show image". Reads and the per-file Both/Difference choice are view state, dropped with a new `files` array, and a landed read joins `folds`, so the place-keeping above covers the placeholder swap. Bytes render only through object URLs made per mounted `<img>` and revoked on unmount (`ObjectImage.tsx`). A host that passes `zoomImage` gets a Zoom control on each comparison, and a click on a version does the same. Both open the file's **zoom window**, the fourth window kind (`imageWindow=1`).
- **Address and read.** Its address, from `imageWindow.ts`, names the versions by reference: a commit's file, or a pull request's. `ImageWindowRoot.tsx` reads them again through `get_commit_file_image` or `get_pull_request_file_image`, never handed bytes, under the pull-request window's content-security policy.
- **Surface.** `ImageZoom.tsx` draws both versions in frames that move in lockstep over one content box, the union of the versions. It allows up to 32× (`imageZoom.ts`; `figureZoom.ts` takes the ceiling as an optional argument) and draws `pixelated` above 100%.
- **Gestures.** The surface follows the platform's: two-finger scroll and the wheel pan natively, a pinch zooms at the pointer (WebKit's `gesture*` events, or a wheel with `ctrlKey` in Chromium and Firefox), and ⌘/Ctrl with `+`, `-`, `0` and `9` zoom as in Preview. Never make a plain wheel zoom there; that is how a trackpad pans. A host whose scroll port has padding sets `--diff-sticky-top` to minus that padding, or rows scroll past above the pinned file headers (`.commit-detail` does). Unified or side by side is `specforge.diffLayout`, per-surface view state like `specforge.railHidden` and never an application setting, since a setting would leak between the desktop and every browser that shares a served instance. Its decisions live in pure, bun-tested modules. Component tests are limited to a few `react-dom/server` renders (`MarkdownView.test.tsx`, `PullRequestView.test.tsx`), and a `src/`-only diff skips the mutation gate:
- `diffLayout.ts`: row pairing, the 104/96 ch fallback, the stored choice, side naming, copy text (which skips folded hunks), and the fold helpers;
- `hiddenChars.ts`: the escapes for characters that render as nothing, reused for any untrusted text;
- `diffHighlight.ts`: one `lowlight` pass per hunk side, memoised;
- `diffFiles.ts`: keys, labels and the navigator tree, plus `isImageFile` and `isLfsPointerFile`;
- `diffImage.ts`: an image read decoded, the size and change wording, the refusal wording, Difference availability, accessible names, and `NearViewQueue`;
- `imageZoom.ts`: the maximized comparison's ceiling, union extents, opening state and sharp-pixel threshold.

`lowlight` is a direct dependency held to the version `rehype-highlight` resolves, as `katex` is held to `rehype-katex`'s.

**Two pull-request panels, four slots, no pane of their own.** `App.tsx` renders `<PullRequestPanel provider="bitbucket" />` and `<PullRequestPanel provider="github" />`, each at one of four JSX positions chosen by that provider's persisted position setting (`PanelPosition` in `src/types.ts`; `bitbucketPosition` / `githubPosition` in `App`): `left-top` (between the Dashboard button and `.sidebar-tree`), `left-bottom` (the default for both — between `.sidebar-tree` and the Archive button), and `right-top` / `right-bottom` (first or last child of the `.rail-column` wrapper around `GraphRail`, which exists only while a panel is positioned in the rail). `panelsAt(slot)` renders BitBucket's then GitHub's, so two panels sharing a slot always stack in that order. A panel hides with its pane, renders nothing while its feature is disabled, and its body is one height-bounded scroll container so the sidebar footer stays reachable. `App` reads each provider's snapshot itself (`usePullRequestSnapshot` in `src/hooks/`) and hands it to the panel, deriving presence with `panelPresent` — never from the panel, which could only report once mounted, and an unmounted panel is exactly what an absent or hidden rail has. While a *present* panel sits in a pane, `App` adds `sidebar-tree--reserve` / `rail-column-graph--reserve`, which keeps the tree (or graph) a fifth of the viewport that the panels yield first — keyed on presence, never on position alone, so a default install (both off at `left-bottom`) lays out exactly as it did without the panels. The pure decisions (sections, counts, reserve) live in `PullRequestPanel.tsx` and are tested there. Collapsed state is per-provider `localStorage` view state (`specforge.pullRequestsCollapsed` for BitBucket, `specforge.githubPullRequestsCollapsed` for GitHub), never a setting.

**The rail exists only while something occupies it.** Its occupants are the commit graph while the *Commit history* setting is on (`get_` / `set_commit_history_enabled`; held in `App` by `useCommitHistoryEnabled`, which starts from the synchronous first-paint mirror in `src/commitHistory.ts`) and any *present* panel in a rail slot. `railHasOccupant` (same module, bun-tested) decides; with no occupant `App` passes `far={null}`, which `SplitPane` already renders as no pane, no divider and no restore chevron — absent, not hidden. The rail's keyboard toggle and the macOS menu event read `railOccupiedRef` and do nothing while it is absent, rather than flipping `railHidden` unseen. Keep the two axes apart: commit history is an application setting shared by every surface, while rail visibility (`specforge.railHidden`) stays per-surface view state. With history off the rail is `.rail-column--no-graph` — panels only, in slot order, the list's 40vh cap lifted — and `useCommitGraph` gets `null`, so no graph read happens.

**Pull requests ↔ worktrees.** `get_pull_request_links` (both transports — no network call, unlike `open_pull_request`, but not free either: a repository's first read after startup or a `.git/config` change spawns one `git remote -v`, off the async runtime) returns which pull requests are linked to which tracked worktrees; the join lives in `openspec-app`, never here. It has no event of its own: `usePullRequestLinks(views)` (`src/hooks/`) re-reads it whenever `views` changes and on either `*-pull-requests-updated`, and `App` hands the snapshot to `DetailPane` (header chips) and both `PullRequestPanel`s (worktree markers). Three rules: a header pull-request chip is a SIBLING of `CopyableIdentity`, never inside it (the name's copy and single tab stop stay untouched); the switcher's `#n` marker is passive text inside the option's button, never a nested control (its visible `#7 +1` is `aria-hidden` and an `.sr-only` list of every number stands in for it, since a `title` never reaches the button's accessible name); and a panel row's worktree marker is a sibling `<button className="pull-request-worktree">` beside the row control in a grid `<li>` — never inside the row's `<button>`/`<a>`, which cannot nest interactive content. An unlinked row carries no class and renders as before. The pure decisions — lookups, where a marker lands (`worktreeDestination`: the worktree's one change, else its most recently modified, else the repository file browser), and the wording — live in `src/pullRequestLinks.ts` and `PullRequestChip.tsx`, and are tested there.

**Settings is five groups, never one column again.** `src/components/settings/` renders Workspaces, Layout, Integrations, Identity and Desktop app one at a time at `/settings/<group>`. `src/settingsGroups.ts` is the membership, order and label source, and it is what decides that the browser skin omits Desktop app; the codec decodes every group on every host, and `App` canonicalises an omitted one in place. A new setting picks a group — a desktop-only one always goes in Desktop app — and is built from the primitives: `SettingsRow` (title and description leading, control trailing), `Switch` (a native `role="switch"` checkbox drawn in accent ink, never an accent fill), `CommittedField` and `CredentialForm`. Never a new free-standing section. The save rule (`settings-view`: *Settings Persist by One Rule*) is what those primitives enforce: switches and choices persist on change, text and numbers only on Enter or blur — never per keystroke — through `src/settingsFields.ts`'s `commitDecision`, credentials only on an explicit Save, and every failed write is reported on its control, never only to `console.warn`. An off integration collapses to one row (`IntegrationCard`); panel slots live in Layout beside the Commit history switch, because together they decide whether the rail exists — and only for integrations that are on: an off provider has no row there at all, not a note saying it is off. The group navigation is a list beside the content when the view is 640px or wider and a native select below — a container query on `.settings-view`, never a media query, since the sidebar and rail narrow the pane. Moving between groups goes through `go()` with no `replace` option on purpose: the overlay rule already replaces, so Back from any group closes Settings. The macOS *Settings…* item (Cmd+,) arrives as the Tauri-only `open-settings` event; nothing registers a Cmd+, keydown of its own.

**Tree selection.** The tree is two levels — a top-level row (repo group or flat workspace) and a change row — and stops there. The contract is the `TreeSelection` union in `src/types.ts`, three variants: `workspace`, `repo`, and `change` (which carries its `TreeContainer` plus the logical change name, never a worktree path). Selections are emitted from `src/components/WorkspaceTree.tsx`.

Adding a variant means updating **two** exhaustive switches in `App.tsx`, not `handleSelect` (which has no switch — it delegates): `repoIdForSelection` and `renderTargetForSelection`. Both are exhaustive over the union with no `default` arm, so `tsc` catches a missed one. There is no third switch: `scrollAnchorForSelection` and its silent `default: return null` are gone with the section and task rows, and `ScrollAnchor` is now the single kind `{ kind: "line"; line }`, produced inside `DocumentView` by the outline and by fragment links rather than by the tree.

**Which artifact and which instance is not a tree question.** A change row resolves to the change's *default artifact* of its *default instance* (`src/changeNavigation.ts` — the same module the header's tab strip reads, so a row click and the strip cannot disagree). Everything below the change — picking another artifact, picking another worktree — happens in the **change header** (`ChangeHeader` in `src/components/DetailPane.tsx`), which `App` places in live mode and `ArchiveView` places in read-only mode. Both write addresses through the existing `go()`, so history, deep links and reader windows are unaffected.
