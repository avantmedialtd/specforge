# Rust workspace

Five crates: two library layers and three frontends. `openspec-core` holds pure primitives; `openspec-app` is the headless service layer that owns the stateful "brain"; `specforge` (Tauri), `specforge-tui` (ratatui) and `specforge-web` (browser) are thin skins over it.

**Where new logic goes.** Parsers, registries, caches and watchers belong in `openspec-core`. Anything stateful that more than one frontend needs — settings, service orchestration, dashboard assembly, quota — belongs in `openspec-app`. Frontend crates should only marshal arguments and call `AppService` / `SettingsStore`. Code parked in a frontend crate is invisible to the other two and is excluded from the mutation gate (`.cargo/mutants.toml`).

- **`crates/openspec-core/`** — no Tauri, no terminal. Cleanly testable from `cargo test`.
  - `registry.rs` — `WorkspaceRegistry` persists registered workspace folders to `workspaces.json`. Registration canonicalises the path and requires an `openspec/` subdirectory.
  - `parser.rs` — parses `tasks.md`, `proposal.md` titles, capability spec directories, and the four-artifact status (`proposal`/`design`/`tasks`/`specs[]`). Task-line format mirrors the artifex VSCode extension.
  - `cache.rs` — `WorkspaceCache`: a plain `HashMap<PathBuf, Vec<ChangeData>>`, passive (the watcher mutates it).
  - `watcher.rs` — `WatcherManager` runs one `notify` + `notify-debouncer-full` watcher per registered workspace, scoped to that workspace's `openspec/` subtree (recursive). On debounced batches it re-parses and emits `CacheEvent` over a tokio broadcast channel. The manager is cheaply cloneable; clones share state via `Arc`. The processing task holds a `Weak<Inner>` so the manager can be dropped cleanly.
  - **`CacheEvent` has far more than the three obvious variants.** Besides `Updated` / `ChangeAdded` / `ChangeArchived` there are `WorkspaceRemoved`, the aggregator's `LogicalChangeAdded` / `LogicalChangeArchived` / `InstanceAdded` / `InstanceRemoved`, plus `GraphChanged`, `QuotaUpdated`, `BitbucketPullRequestsUpdated` and `GithubPullRequestsUpdated`. In a git repository the aggregator emits the `Logical*` pair, **not** `ChangeAdded` — code that only matches `ChangeAdded` silently does nothing there. Never write a wildcard arm over `CacheEvent` without deciding what each ignored variant means.
  - `self_write.rs` — `SelfWriteTracker` records paths the app just wrote so the watcher can ignore the resulting events.
  - `wsl.rs` + WSL support — **Windows-only**. Workspaces in the WSL2 filesystem (reached via `\\wsl.localhost\<distro>\…`) are handled specially because the 9P share is deaf to `ReadDirectoryChangesW` and hostile to Windows `git.exe`. `wsl.rs` is pure path logic (detection, Linux↔UNC translation, `wsl.exe` argv building) — cross-compiled and unit-tested on every platform, inert off Windows. The two *backends* are `#[cfg(target_os = "windows")]`-gated: `watcher.rs` swaps in a `notify::PollWatcher` (re-scan cadence default **10s**, configurable via `wslPollIntervalSecs`, surfaced only on Windows), and `git.rs`'s `git_command(GitAnchor, args)` chokepoint routes every git call through `wsl.exe -d <distro> git …`, translating paths back to UNC. macOS/Linux builds carry none of this. `paths::canonicalize` (dunce-backed) is used at every `RepoId`-forming site so verbatim/UNC forms never split one repo into two identities. The 9P-runtime behaviour needs a real Windows+WSL2 box to verify.
    **No CI job compiles those `cfg(windows)` backends at all** — every runner is `ubuntu-latest` — so they can be broken by a refactor or a dependency bump without a single job going red. Compile-check them before you trust such a change: `cargo check --target x86_64-pc-windows-msvc -p openspec-core --all-targets` (add `clippy … -- -D warnings` to catch a deprecation, which CI treats as an error). The same trick is worth using for Linux from a macOS checkout — `--target x86_64-unknown-linux-musl` — because a dependency's per-platform type aliases can differ from macOS's; `notify-debouncer-full`'s `RecommendedCache` is `FileIdMap` on macOS and `NoCache` on Linux, so a type that compiles locally can still fail on the runner.
  - `types.rs` — `serde(rename_all = "camelCase")` on the structs that cross the IPC boundary, but **string-valued enums use `kebab-case`** (see `PaletteColor`). Harmless while every variant is one word; a multi-word variant would silently break the matching union in `src/types.ts`.
  - **On an enum, `rename_all` renames the VARIANTS — not the fields inside a struct variant.** Those need `rename_all_fields = "camelCase"` (serde ≥ 1.0.184) as well. On a plain struct `rename_all` *does* rename fields, so the same attribute means two different things depending on what it is attached to, and the wrong one looks correct. This has shipped twice: `ArchiveScope::Repo { repo_id }` broke every repository-scoped archive listing at runtime, and `WorkspaceView::Flat { display_name }` silently dropped every flat workspace's display name (the tint in the same dialog applied, because `color` is one word — so half the user's edit took effect). Both were invisible to every gate: `cargo test` builds values in Rust and asserts on Rust, `tsc` checks the mirror against itself, and an attribute is not a mutable line so `cargo mutants` cannot reach it. Adding a struct variant to a serialized enum? Add the attribute. `crates/openspec-app/tests/wire_shape.rs` is the behavioural guard — it serializes every **command return type** the frontend reads and fails on any snake_case key at any depth; extend its fixtures when you add a root, a field, or a variant. Know its edges before trusting it: it covers neither **event payloads** (`events.rs`'s own `#[cfg(test)]` module does, partially) nor **argument types the frontend sends** (`types.rs`'s `wire_shape_tests` covers `ArchiveScope`/`FileScope`, and the deserialize direction is where the `ArchiveScope` bug actually failed), and it checks key spelling rather than key identity, so a *rename* to another camelCase spelling passes. String-valued enums are asserted separately in the same file, by exact wire value — the underscore predicate cannot see them, and a dropped `rename_all` yields `"StaleVsArchived"`, which has no underscore anyway.
  - `diff.rs` — the diff model every diff surface renders (`DiffFile`, `FileStatus`, `DiffContent`, `Hunk`, `Line`) and its two pure parsers: `parse_diff` for a full unified diff as git writes it and BitBucket serves it (extended headers, git's C-quoted paths, the no-newline marker folded into the line before it, a type change folded into one file), and `parse_hunks` for a header-less per-file patch such as GitHub's `patch` field. Also the line and byte budgets (`eager_by_lines`, `ByteBudget`, `eager_files`, `withhold_files` and their `pub const` limits), which decide which files arrive with hunks and which are `Withheld` until a reader asks. They are pure so `openspec-app` can apply the same decision to a pull request's in-memory detail. `diff_versions` is the local diff of a file's two versions, on the `similar` crate, for a file GitHub sent without its patch: binary on a NUL byte or invalid UTF-8, too large past the 8 MiB per-file ceiling, and otherwise hunks through `parse_hunks`. The one hunk reader also reports each hunk's **body** byte range: the bytes past its `@@` line, header excluded. The functions are `parse_hunks_with_bodies`, `SpannedFile.hunk_bodies` and `diff_versions_with_bodies`, which `openspec-app` digests to key hunk marks. `Hunk` itself never carries them. `FileStatus` and `DiffContent` are tagged unions, so they carry `rename_all_fields` as well as `rename_all` (the `ArchiveScope` trap above).
  - Also here, and larger than everything above: `repo_view.rs`, `git.rs`, `dashboard.rs`, `activity_log.rs`, `presentation.rs`, `repo_monitor.rs`, `repo_cache.rs`, `identity.rs`, `graph.rs`, `garden.rs`, `files.rs`, `paths.rs`. Working-tree status, the commit graph, dashboard assembly, the activity log and per-row presentation/disable state all live in these — check before adding a module.
  - **`git.rs`'s commit reads stop git on purpose.** `commit_base`, `commit_file_list`, `commit_patch` and `commit_file_diff` read a commit in a fixed number of processes, whatever its file count: one `rev-list --parents`, one `diff-tree -z --raw --numstat` list, and one streamed `diff-tree --patch` that stops once the last eager file's section is complete (or a byte limit is reached). A read that stops early drops the pipe, kills the child and reaps it, and that deliberate stop counts as a successful read, not as the failed exit the `.output()` pattern would report; a read that reaches the end of the output is only reaped. A file with no changed lines (a mode-only change, a pure rename, an empty file) is known to have no hunks without being read, except a type change, whose `0 0` numstat can still hide two hunks. Every revision comes from `commit_base` and goes after `--end-of-options`, and every path after `--` as `:(literal)…`.

- **`crates/openspec-app/`** — the headless application service. Depends on neither Tauri nor a terminal, so orchestration stays testable and identical across frontends.
  - `service.rs` — `AppService`: dashboard assembly, first-launch backfill/seeding, watcher lifecycle, link resolution.
  - `settings.rs` — file-backed `AppSettings` + `SettingsStore` + `WebServerConfig`, shared by all three frontends. **Launch-on-login is not stored here** — it lives in the OS via `tauri-plugin-autostart` (driven from `crates/specforge/src/commands.rs`) and is queried fresh each time.
  - `events.rs` — **the source of truth for every event name and payload shape** (`cache-updated`, `change-added`, `change-archived`, `workspace-removed`, `logical-change-*`, `instance-*`, `graph-changed`, `quota-updated`, `bitbucket-pull-requests-updated`, `github-pull-requests-updated`, `workspace-presentation-updated`, `document-width-changed`, `pull-request-panel-moved`, `commit-history-enabled-changed`, and the macOS-only menu events `toggle-sidebar` / `toggle-commit-rail` / `open-settings`). `event_envelope` maps a `CacheEvent` to its wire form. Both the Tauri forwarder and the web SSE bridge go through here; `src/types.ts` re-declares the same string literals by hand. The two **service notices** live here too: `review-progress-changed` (the reference) and `pull-request-provider-changed` (`{ provider, enabled }`), as `ServiceNotice` with `notice_envelope`. `AppService` raises them on its own broadcast (`notify`/`subscribe_notices`); they are never a `CacheEvent` variant and never a direct emit from a command.
  - `config.rs` — `config_dir()` and `APP_IDENTIFIER` (`com.avantmedia.specforge`). Every instance resolves the same directory, which is why concurrent worktree apps share state.
  - `quota.rs` / `chatgpt_quota.rs` — the opt-in usage pollers (off by default).
  - `bitbucket.rs` — the opt-in BitBucket pull-request poller (off by default): the read recipe ported from artifex, the review summary, the snapshot the BitBucket panel renders, and half of the `open_pull_request` URL check's data. Its credential is write-only — `settings.rs` never hands the token to anything but this poller.
  - `github.rs` — its structural twin for GitHub (off by default): one compile-time constant GraphQL query per refresh (authored + review-requested), the GitHub-aware rate-limit verdict (403/429 headers, secondary-limit bodies, `RATE_LIMITED` in a 200), the row signals (checks, conflicts, unresolved conversations), and the other half of the `open_pull_request` check. Its token is write-only on the same terms; `GH_TOKEN` then `GITHUB_TOKEN` override it. The twins share the loop's *shape*, not its code — see `chatgpt_quota.rs` for why.
  - `pull_requests.rs` — the row types both panels render (`PullRequestSummary`, `ReviewSummary`, `ChecksState`, `PullRequestsStatus`) and the shared newest-first merge. Neither provider module owns the other's wire shape.
  - `pull_request_links.rs` — the pure join behind `get_pull_request_links`: both providers' rows against each warm repository's worktree branches/upstreams (`RepoView.worktree_refs`, never serialized) and remotes. The matching rule is shaped against two false positives — a fork's same-named branch and the shared branch a worktree was created from (see the `pull-request-worktree-links` spec before loosening it). The remotes come from `WatcherManager::remotes`, a memo read lazily (one `git remote -v` per warm repo, never for a disabled one) and dropped by `invalidate_remotes` when `repo_monitor.rs`'s `remotes` concern — `.git/config` only, deliberately not `refs/remotes/*` — fires; that concern also runs `refresh_status_for`, which is what re-reads upstreams changed through config alone.
  - `usage_http.rs` — the blocking request posture all four pollers share: a GET for three, a POST (redirects off) for GitHub; the `Authorization` header, `proxy(None)`, the status verdicts. The pull-request detail reads add a no-redirect GET (`get_without_redirects`). The four pollers, the detail reads and the file reads are the app's **only** runtime network calls, and either read only ever targets a pull request a poller already lists. A file read (`github_detail::read_file_with`) loads one file GitHub sent without its patch: a compare for the merge base, once per cached detail, and the file at the merge base and at the head through a raw GET (`send_get_raw`), under the detail read's limits.
  - **The pull-request viewer's service half:**
    - `pull_request_detail.rs`: the `PullRequestReference` every command takes (case-insensitive owner/repo, a hashable `key()`), its snapshot lookup `listed_row`, and the detail model.
    - `pull_request_limits.rs`: provider-owned deadlines shared by a provider's poller and its detail reads (GitHub keeps GraphQL and REST apart), plus the hourly detail budget and the in-flight gate.
    - `github_detail.rs` / `bitbucket_detail.rs`: the recipes. GitHub sends one compile-time constant query with variables, plus REST files pages. BitBucket follows its payload's own links.
    - `pull_request_cache.rs`: the 32-entry detail cache, with the freshness rule, single flight and withheld-file reads. `file()` answers a ready file, what a file read must fetch, or `FileChanged`; `keep_fetched` keeps a file read's result and the merge base only under the same generation and commits.
    - `pull_request_read.rs`: the injected I/O, so every read is tested hermetically.
    - `review_progress.rs`: `review-progress.json`.
      - **File keys:** the SHA-256 of the patch bytes as received, else GitHub's blob id, else the head commit.
      - **Hunk keys:** the SHA-256 of each hunk's body, from `CachedFile.hunks`, numbered among identical bodies (`#n`), and stored under `hunks`.
      - **One write rule:** every write goes through `MarkWrite::apply`, which keeps a file viewed exactly when every hunk is. A stale file key survives hunk marks, and unmarking one hunk of a file marked whole writes the others out first.
      - **States:** derived, `partlyViewed` included.
      - **Pruning:** only on complete lists.
    - `window_title.rs`: the window-title sanitiser.

    A credential change goes through the `AppService` setters on every transport. They drop that provider's cache, advance its generation, notify, and publish `unavailable` when it is re-enabled inside a deadline. Writing the flag straight to settings would skip all of that.

- **`crates/specforge/`** — Tauri shell. Thin by design.
  - `lib.rs` — the `run()` entry point. Order matters: install the event forwarder *before* populating the cache (initial `add_workspace` calls don't emit `Updated`, but later edits do — so the forwarder needs to be live first). Cache is populated synchronously via `block_on` so the frontend's first `get_changes` doesn't race a watcher startup. Also holds the `tauri::generate_handler![…]` list — a new command must be registered there.
  - `commands.rs` — `#[tauri::command]` handlers that deserialize args and call `AppService` / `SettingsStore`. The path-traversal guard on artifact reads lives in the shared layer, not here — don't re-add a second one.
  - `events.rs` — only the Tauri forwarding sinks: `spawn_event_forwarder` maps each `CacheEvent` through `openspec_app::event_envelope` and emits it, and `spawn_notice_forwarder` does the same for the service notices through `notice_envelope`, to every window. Names and shapes belong to `openspec-app`.
  - `reader.rs` + `pull_request_window.rs` — one detached-window helper and its two kinds. Readers are `reader-<hash>` with `?reader=1`, unchanged. Pull-request windows are `pull-request-<hash>` with `?pullRequest=1&at=…`; their size is remembered in settings, clamped to the work area, at least 600×400, and their title is sanitised and follows the page through the title-change hook. Each kind has its own capability: `default.json` matches `main` and `reader-*`, and `pull-request.json` grants a pull-request window only listen, unlisten and close. Window-building commands are `async`, because a sync one deadlocks on WebView2.
  - `tray.rs` + `tray_icon.rs` — system tray. The badge updater subscribes to the same `CacheEvent` stream as the forwarder; on macOS the badge is set via `set_title`. There are **two** glyphs — `icons/tray-icon.svg` (`TrayGlyph::Default`) and `icons/tray-specs.svg` (`TrayGlyph::Specs`, shown when any active change has capability specs, flipped live by `spawn_tray_glyph_updater`). Edit both together. Each is rasterized per-monitor at the active scale factor and re-rasterized when the window moves between displays with different scales. macOS template rendering requires **pure black + alpha** — `rasterize` debug-asserts every output pixel has R=G=B=0.
  - `notifications.rs` — desktop notifications fire on `ChangeAdded` **and on `LogicalChangeAdded`** (the variant that actually fires for git repos), plus the archive counterparts; `Updated` never notifies, by design. Gated by `settings.notifications_enabled` and further suppressed per-row for parked/disabled rows — check both before concluding a notification path is broken.

- **`crates/specforge-tui/`** — the terminal frontend. One binary, three faces: the interactive TUI, `--status` (snapshot and exit) and `--line` (one ambient status line). All three drive the same in-process `AppService`, with no IPC.

- **`crates/specforge-web/`** — the local web server: an embedded mode the desktop app's serve toggle drives, and a standalone binary `specforge-serve`, released alongside `specforge-tui` for macOS/Linux/Windows (see `release-pipeline`).
  - `dispatch.rs` is the `/api/invoke` command table — **one arm per Tauri command**. See `src/CLAUDE.md` for the parity rule; a missing arm is a runtime-only failure.
  - Bind resolution is `--bind <addr>`, else the `SPECFORGE_WEB_BIND` env var, else `127.0.0.1`. It is deliberately never a `WebServerConfig` field, because that struct is shared with the desktop app's embedded toggle — don't add a settings control for it by reflex. A non-loopback bind disables the request-authority allowlist; see the `web-ui` capability spec for the trust-boundary contract.
