# SVG tray-icon rasterization — design

## Context

The current tray installation (`crates/specforge/src/tray.rs:19-23`) reuses the application's window icon as the tray glyph:

```rust
let icon = app
    .default_window_icon()
    .cloned()
    .expect("default window icon must be configured in tauri.conf.json");
```

That window icon comes from `tauri.conf.json` and resolves to a fixed-resolution PNG generated by `tauri icon` from the master in `crates/specforge/icons/icon.png`. Two consequences:

1. The tray glyph and the dock/app icon are *the same* asset — any change to one moves the other.
2. The tray glyph's pixel resolution is whatever the PNG bake produced (typically @1x and @2x). On a 3x retina panel the OS up-scales; on a 1.5x Windows panel it down-scales with a small loss.

`TrayIconBuilder::icon_as_template(true)` is currently set (`tray.rs:37`), which on macOS recolours the icon to match the menu-bar foreground using the alpha channel. This already constrains the source PNG to a black silhouette — we are continuing that contract, just from a vector source.

No external stakeholders. Engineering preference + product polish.

## Goals / Non-Goals

**Goals:**

- Make `crates/specforge/icons/tray-icon.svg` the canonical source for the menu-bar / tray glyph.
- Rasterize at the active monitor's pixel density so the tray icon is crisp on 1x, 1.5x, 2x, and 3x displays without checking in multiple raster sizes.
- Decouple the tray glyph from the app/dock icon so each can evolve independently.
- Preserve macOS template rendering (light/dark menu-bar inversion keeps working).
- Add no new system-library dependencies (notarisation surface stays clean).

**Non-Goals:**

- Replacing the app, dock, or installer icons with SVG sources — `icon.png`, `icon.icns`, `icon.ico` and the sized variants stay as-is, generated by `tauri icon`.
- Tracking which physical monitor renders the menu bar in multi-display setups (we re-raster on the *main window's* scale change, which is the common trigger).
- Animated or stateful tray icons (e.g., spinner during a sync).
- SVG editor / design tooling. The SVG is authored externally and committed.

## Decisions

### Use `resvg` + `usvg`

Pure-Rust, no system libs. The two-crate split (`usvg` parses + simplifies, `resvg` paints into a pixmap) is the documented entry point — we take both.

Alternatives considered:

- **`librsvg`** — rejected: pulls a GTK stack on Linux and a Homebrew dep on macOS dev machines; messy under notarisation.
- **`tiny-skia` alone** — rejected: drawing primitives only, we'd reinvent `resvg`.
- **`nsvg`** — rejected: unmaintained.

### Rasterize at startup, re-raster on scale change

The tray icon is small (~22pt on macOS, ~16px on Windows/Linux). Raster cost is trivial; we don't need build-time rasterization or caching. Flow:

```
   startup ──▶ app.primary_monitor().scale_factor()
                       │
                       ▼
              rasterize_tray_icon(SVG, 22, scale) ──▶ tauri::image::Image
                       │
                       ▼
              TrayIconBuilder::icon(image).build()

   later ──▶ WindowEvent::ScaleFactorChanged { scale_factor, .. }
                       │
                       ▼
              rasterize_tray_icon(SVG, 22, scale_factor)
                       │
                       ▼
              tray.set_icon(Some(image))
```

Alternative considered: `build.rs` pre-rasterizes a fixed set of sizes. Rejected — same drift problem we have today, just moved to build time, and gives up the runtime sharpness story.

### Bundle the SVG with `include_bytes!`

The SVG is compile-time-known and tiny. No reason to read from disk at runtime — bundling makes the binary self-contained and makes the template-correctness check (below) load-bearing exactly once per compile.

### Preserve macOS template rendering, fail loud on drift

`icon_as_template(true)` stays. For it to work:

- All SVG fills must resolve to `#000` (or default to black).
- Edge anti-aliasing produces partially-transparent black pixels — macOS handles that.
- Any non-black colour leaks through as grey on macOS dark mode.

To catch authoring mistakes early, `rasterize_tray_icon` runs a debug-build assertion that walks the output buffer and panics if any pixel has non-zero R, G, or B. Release builds skip the loop. Since the SVG is `include_bytes!`-bundled, the check only needs to pass at compile-cycle time on a developer machine.

### Separate the tray glyph from the app icon

Stop reusing `default_window_icon()` for the tray. The two assets are different design problems:

```
   tray-icon.svg            icon.png (+ .icns / .ico)
   monochrome silhouette    full-colour artwork
   ~16-22 logical px        1024 px master
   template-rendered        rendered as-is
   menu bar / system tray   dock, switcher, installer, file
```

Splitting them is the right long-term shape regardless of rasterization strategy; doing it inside this change keeps scope honest.

## Risks / Trade-offs

- **[Template-colour drift]** — a future SVG edit introduces a non-black fill, breaking macOS template rendering silently. → **Mitigation**: debug-build pixel-walk assertion in `rasterize_tray_icon` panics CI / dev builds the first time the SVG is rasterized.
- **[Multi-monitor menu-bar mismatch]** — main window on a 2x display, menu bar on a 1x display: tray icon is rasterized for 2x and the OS will downscale on the actual menu-bar monitor. → **Mitigation**: accepted for v1; the visible defect is mild (slightly soft icon, not broken). Future work: subscribe to monitor topology changes directly.
- **[Binary size growth]** — `resvg` + `usvg` add several hundred KB. → **Mitigation**: acceptable for a desktop app; size budget isn't currently load-bearing.
- **[`resvg` parser surface]** — the crate parses SVG, increasing attack surface in principle. → **Mitigation**: the input is a single SVG bundled at compile time from our own repo; no runtime untrusted input.
- **[`include_bytes!` recompile churn]** — every SVG edit triggers a Rust rebuild of the `specforge` crate. → **Mitigation**: design intent — the SVG is part of the binary contract.

## Open Questions

- **Who authors `tray-icon.svg`?** For v1 we ship a placeholder — a solid-black silhouette traced from the existing logo. Mark `TODO(design)` and link a follow-up. Not blocking, since the wiring and rasterization are what we're verifying.
- **Logical size per platform.** macOS menu bar wants ~22pt; Windows/Linux tray ~16px. Do we pick one logical size and let the OS scale, or branch per `cfg(target_os = ...)`? Default plan: single 22pt logical size, accept the slight upsize on non-macOS until we see it in practice.
