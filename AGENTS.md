# SpecForge agent guidance

## Workflow and contracts

- Start coding **and exploration** in a dedicated git worktree. Enter it before `openspec new change <name>` so scaffolding lands in the right checkout; use tool working directories rather than shell `cd`.
- **Use OpenSpec proactively:** create a change before implementing new or changed product behavior, without waiting to be asked (or continue an existing change covering it). Routine bug/crash fixes that only restore intended behavior do not require a new change.
- Before changing behavior, read the relevant `openspec/specs/<capability>/spec.md` and active change artifacts. Artifact-writing rules live in `openspec/config.yaml`.
- Read the relevant layer guide before editing: `crates/CLAUDE.md`, `src/CLAUDE.md`, or `site/CLAUDE.md`.
- **SpecForge** is the product; **OpenSpec** is the format and `openspec/` layout. The published npm wrapper is `@avantmedia/specforge`, never unscoped `specforge` (an unrelated package). See `openspec/specs/product-identity/spec.md`.

## Where logic belongs

- `crates/openspec-core` owns parsers, registry, cache, watchers and git primitives. Shared state/orchestration belongs in `crates/openspec-app/src/service.rs` (`AppService`) and `crates/openspec-app/src/settings.rs` (`SettingsStore`).
- `specforge` (Tauri), `specforge-tui`, and `specforge-web` are thin adapters over that service. The same React bundle runs in desktop and browser through `src/api.ts`; frontend-local domain logic does not reach the other hosts.
- The app never changes local work or git state and never merges pull requests. Only native desktop submits reviews, after explicit confirmation; browser and terminal do not.

## Build and verification

Use Bun. In a fresh worktree, run `bun install --frozen-lockfile`, then `bun run build` **before workspace Rust builds, clippy or tests**. Both Tauri's `generate_context!` and web's `RustEmbed` require gitignored `dist/` at compile time. Focused library tests avoid that prerequisite.

| Scope | Command |
| --- | --- |
| Frontend CI checks | `bun run lint`, then `bun test`, then `bun run build` (strict typecheck + bundle) |
| One frontend test file | `bun test <path>` |
| Rust formatting | `cargo fmt --all -- --check` |
| Rust lint | `cargo clippy --workspace --all-targets -- -D warnings` |
| All Rust tests | `cargo test --workspace` |
| One Rust integration suite | `cargo test -p openspec-core --test parser` (targets live in `crates/<crate>/tests/`) |
| One Rust test by name | `cargo test -p <crate> <name_substring>` |
| IPC serialization guard | `cargo test -p openspec-app --test wire_shape` |
| Native-shell smoke build | `bun tauri build --debug --no-bundle` |

- Rust tests spawn real `git`; it must be on `PATH`. Linux workspace builds need the Tauri system libraries listed in `.github/workflows/ci.yml`.
- Keep root `bunfig.toml`'s site exclusion: otherwise `bun test` collects Playwright `*.spec.ts` and fails at `test.describe()`.
- Mutation CI gates changed source lines in **only `openspec-core` and `openspec-app`**. After `git fetch origin master`, save `git diff "$(git merge-base origin/master HEAD)" HEAD` to a file and run `cargo mutants --in-diff <diff-file>`; this checks committed changes. Configuration/exclusions live in `.cargo/mutants.toml`. Never bypass a failing baseline with `--baseline=skip`; a green skipped job says nothing about frontend coverage.
- Rust suppressions use `#[expect(lint, reason = "...")]`, not `#[allow]`. Oxlint also rejects unused disable directives; an exhaustive-deps disable must sit directly above the dependency array.

## Running and inspecting the UI

- Browser loop, after building: start `cargo run -p specforge-web --bin specforge-serve`, then `bun run dev` in another process. Vite's strict port 1420 proxies `/api` to 4317; set `SPECFORGE_WEB_PORT` consistently if changing the backend port. Vite alone has no working backend.
- For native tray/window/notification checks, use `bun run wt:dev`, not competing fixed-port `bun tauri dev` instances. `bun run wt:dev --print` shows the assigned slot without launching. Run visual checks yourself.
- Worktree apps and the standalone server share the **real** `com.avantmedia.specforge` config directory; they are not state-isolated sandboxes. Debug web serving reads `dist/` from disk per request: rebuild before trusting a served UI check.

## IPC and permissions

- A shared command needs the wrapper in `src/api.ts`, handler in `crates/specforge/src/commands.rs`, `generate_handler!` entry in `crates/specforge/src/lib.rs`, and web arm in `crates/specforge-web/src/dispatch.rs`. Also sync `crates/specforge/build.rs`'s `APP_COMMANDS` and grant only the required window capabilities; do not edit or commit generated `crates/specforge/permissions/autogenerated/`.
- Do **not** add web parity for desktop host-opening operations, credential setters or review actions. Their web refusals/absent dispatch arms are deliberate security boundaries, pinned by tests.
- Event names/payloads belong in `crates/openspec-app/src/events.rs`; keep the TypeScript mirror and desktop forwarding/web SSE behavior aligned.
- Rust IPC types are hand-mirrored in `src/types.ts`; there is no codegen. Preserve each type's wire casing. Enum struct-variant fields need `rename_all_fields = "camelCase"`—`rename_all` alone only renames variants. Extend `crates/openspec-app/tests/wire_shape.rs` fixtures when adding fields, variants or return types.

## Separate site and distribution

- `site/` has its own install, lockfile and toolchain; root install/build/typecheck do not cover it. Run site commands with cwd `site/` or use root `site:*` scripts: plugins resolve and write paths relative to cwd. `site/site-kit/` is a vendored fork, not a package dependency.
- Site E2E (`bun run site:test`) uses preview, not dev: first build with `bun run site:build` and install Chromium via `bunx playwright install chromium` with cwd `site/`. Unit tests are `bun run site:test:unit`; the full site gate is `.github/workflows/site.yml`.
- CLI/platform changes to `specforge-serve` must also update `npm/packaging.mjs`; read `npm/README.md`. Published manifests are generated, not committed; focused checks are `bun test npm/`.
- Release versions come from `v*` tags; tracked manifest `0.1.0` values are intentional. Read `.claude/commands/release.md` before releasing: versioned notes and `site/src/site-config.ts` must match the tag.
- After any upstream push, monitor the GitHub workflows (`gh run list --branch <branch>`, `gh run watch <id>`); inspect failures with `gh run view <id> --log-failed` and report the result.
